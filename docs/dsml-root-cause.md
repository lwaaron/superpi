# DSML 畸形输出的真因取证：三次假设、三次证伪

日期：2026-11-21 · 数据源：`~/.pi/agent/sessions/` 下 50 个真实会话文件

## 0. 结论摘要

**真因不是上下文规模，不是图片堆积，也不是 thinking 通道串流。**

36 条畸形输出有一致的形态：**只有 DSML 的闭合尾巴，没有开头**，
因此**结构化 toolCall 从未形成**，**工具从未执行**，本轮空转，
用户只能手打「继续」重试（36/36 次）。

这篇文档的价值主要在**过程**：三次看起来合理的假设，全部被数据否定。
在这个问题上，直觉与"合理推断"彻底失效，只有逐条数形态才能找到真因。

---

## 1. 第一次假设：上下文超载 → **证伪**

### 假设

`before/budget` 中位数 403%（每轮超预算 4 倍），模型在陌生上下文上退化。

### 反面证据

| 观测 | 值 |
| --- | --- |
| `trimmed=true` 占比 | **240/240 = 100%** |
| `before` 范围 | 2,849,944 ~ 2,919,604（恒定） |
| 畸形的分布 | 只在会话**后 10%** 出现 |

一个覆盖全部样本的条件（每轮都裁剪、before 恒定），无法解释只在少数样本出现的结果。
**这是相关，不是因果** —— `AGENTS.md` §5.0.1 在 0.15.4 已经为此误判过一次。

### 结论

上下文超载是**背景条件**，不是触发因素。0.17.0（写入时图片限额）治的是真实的
上下文浪费（图片占 47%，收益 -96.6%），但**它不是 DSML 的修复**。

---

## 2. 第二次假设：图片堆积 → **证伪**

### 假设

图片占 47%（118 张 × 12000 tokens），堆积到后期导致退化。

### 支持它的表面证据（险些导致误判）

| 图片累计桶 | assistant 条数 | 畸形条数 | 出现率 |
| --- | --- | --- | --- |
| 0 张 | 1195 | 0 | 0.00% |
| 1-4 张 | 1719 | 1 | 0.06% |
| 5-16 张 | 77 | 0 | 0.00% |
| 17-64 张 | 405 | 0 | 0.00% |
| 65+ 张 | 874 | 36 | **4.12%** |

表面上是漂亮的单调上升。

### 致命反驳（两次核对才成立）

**① 全部 36 条畸形来自同一个会话文件。**
65+ 桶的畸形 100% 集中在那个 118 张图的会话里 —— 这是单例效应，不是统计规律。

**② 在同一个会话内部，图片早就有了。**
- 图片首次出现：第 **318** 条 assistant（15.2% 处）
- 畸形首次出现：第 **1881** 条 assistant（90.0% 处）
- **中间 1563 条 assistant 在"图片很多"的状态下零畸形**

### 结论

「图片堆积导致 DSML」**被否定**。

### 这一条留下的方法教训

看到"单调上升"就想要支持假设，是 0.15.4 那个错误的翻版。
**必须做的一项检查**：每个桶的贡献是否集中在少数文件上。
本次正是这个检查救了它 —— 如果只报告桶级出现率，结论会完全相反。

## 3. 第三次假设：thinking 通道串流 → **证伪**

### 假设

畸形条平均无 thinking、无 toolCall、正文 627 字符（正常条 84），
且样例里 `</thinking>` 出现在 text 块中 → 推测 thinking 与正文通道边界丢失。

### 反面证据

| 判据 | 结果 |
| --- | --- |
| 畸形条含 `</thinking>` | **6 / 36 = 17%** |
| 正常条含 `</thinking>` | 9 / 2054 = 0.44% |

只有 17% 命中。我看到的前两个样例恰好都含该特征 —— **被两个样本误导了**。

### 结论

「thinking 串流」**不足以解释 36 条**。是必要不充分条件，不是真因。

---

## 4. 真因：模型只输出了结构化的"尾巴"

### 形态统计（36 条，逐条核对）

| 特征 | 命中 |
| --- | --- |
| 有开头 `<｜｜DSML｜｜ invoke` | **0 / 36** |
| 只有闭合 `</｜｜DSML｜｜ invoke>` | 34 / 36 |
| 只有闭合 `</｜｜DSML｜｜ calls>` | 35 / 36 |
| 含 `<parameter name=`（参数文本） | 31 / 36 |
| 同条有结构化 `toolCall` 块 | **0 / 36** |
| 之后有 `toolResult`（工具真的执行了） | **0 / 36** |
| 之后紧跟用户手打「继续」 | **36 / 36** |

### 原文样例

```
版本门禁通过。跑完整门禁再提交：

<parameter name="bash">cd /d/my_projects/SuperPi/SuperPi && timeout 900 npm test ...</parameter>

</｜｜DSML｜｜ invoke>
</｜｜DSML｜｜ calls>
```

### 完整因果链

```
模型输出：[正文] + <parameter name="bash">命令</parameter> + 闭合标签
          ↑ 缺少开头 <｜｜DSML｜｜ invoke
          ↑ 没有形成结构化 toolCall 块
          ↓
工具从未执行（0/36 有 toolResult）
          ↓
本轮空转结束：屏幕上只有一段文本，什么都没发生
          ↓
用户手打「继续」重试（36/36）
```

### 这意味着什么

**这不是"模型不知道怎么写工具调用"**。参数文本完整存在（31/36），
说明它已经决定了要调用什么。缺的是**开头的 `<｜｜DSML｜｜ invoke` 没有进入输出流**。

即：结构化的**头部**丢失，只有**尾巴**到达。问题更可能在
**流式解码/组装层**，而不是模型的理解层。

### 尚未区分的三种可能（数据不足）

1. **pi 的流式解析**在特定条件下把 DSML 头部当成了别的什么而丢弃；
2. **provider 的流式重组**在长工具序列下丢失首帧；
3. **模型自身**在连续长工具序列下退化成"只记得尾巴"。

要区分它们，需要抓一次**原始 SSE 流**（`provider_stream_event` 事件），
看 DSML 头部在到达 pi 之前是否还存在。这一步没做。

## 5. 方法教训（比结论更重要）

### 5.1 三次假设全部错在同一个地方

| 假设 | 错法 |
| --- | --- |
| 上下文超载 | 用**覆盖全样本的条件**解释局部现象 |
| 图片堆积 | 用**单例效应**冒充统计规律 |
| thinking 串流 | 用**两个样例**代表 36 条 |

三次都是「先有合理解释，再去找支持它的证据」。正确顺序是反的：
**先把 36 条逐条数出形态，再问什么样的机制能产生这个形态。**

### 5.2 必须固化的两个检查

1. **桶级统计必须看贡献集中度**：某个桶的异常若来自单一文件/单一样本，
   那不是规律，是案例。
2. **形态统计要逐条数，不要抽样看**：我看前 2 个样例得到的结论，
   与看全部 36 条得到的结论完全相反（`</thinking>` 17% vs 直觉的高比例）。

### 5.3 一个反面教材

`AGENTS.md` §5.0.1 已经记录过 0.15.4 把相关当因果的错误，
而本次前两个假设又在重复同一个动作。**规则写在文档里不等于会执行** —— 
这说明需要的是**可执行的检查动作**（上面的 5.2），不是提醒。

### 5.4 判据本身也被修正了两次（必须记下来）

把结论固化成可复现探针（`_scratch/probe-dsml-morphology.mjs`）时，
判据被推翻重写了两次。这两次都差点让结论变成假的：

**修正一：误报排除**

第一版判定 `含 DSML 且不含讨论关键词`。扫全量 50 个文件时得到 37 条（不是 36），
且出现「1 条有结构化 toolCall」的矛盾。查证那 1 条：是我在**改检测器时正文里
引用了 `</｜｜DSML｜｜ calls>` 这段字面量** —— 它带 toolCall、有 toolResult，
明显不是畸形。是误报。

修正：判据改为「**没有**结构化 toolCall」+「标记在正文**末尾** 300 字符内」。
理由是这两条**从 36 条真实畸形的形态里读出来的**，不是先验设定。

**修正二：窗口边界（更险的一次）**

用固定窗口（`slice(i+1, i+4)`，看后 3 条）统计「之后有 toolResult」，
得到 **31/36** —— 与之前「0/36」的结论完全相反，探针直接 FAIL。

查证真实序列：

```
畸形轮 assistant
  → user「继续」        ← 用户手打
  → assistant（重试轮）
  → toolResult          ← 属于重试轮，不是畸形轮
```

固定窗口跨过了轮次边界，把**重试轮**的 toolResult 算进了畸形轮。

修正：只看「到下一个 assistant 为止」。结果回到 **0/36**，与结论一致。

**教训**：`0/36` 与 `31/36` 之间的差别不是数据，是**窗口定义**。
如果第一次跑就得到 31/36，我很可能直接改结论为「工具其实执行了」——
那会是完全相反的错误结论。**探针必须能自校验，而自校验的前提是判据写清边界。**
