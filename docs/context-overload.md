# 上下文超载取证：为什么 285 万 tokens，以及为什么只能在写入时治

日期：2026-11-20 · 版本：0.17.0

## 0. 一句话结论

**`context` 层的裁剪是每轮重算的临时视图，永远改不动历史本体。**
实测一个真实会话：`before` 恒定 285 万 tokens、`imagesDropped` 240 轮恒为 117、
压缩比恒定 4.40x —— 两个"恒定"就是「每轮重算同一件事」的指纹。
唯一能降低 `before` 的位置是 `tool_result`（写入时），不是在 `context`（读时）加更多折叠规则。

---

## 1. 现象与取证

### 1.1 数据来源（都是真实发生的，不造实验）

| 数据 | 位置 | 规模 |
| --- | --- | --- |
| 会话事件流 | `~/.pi/agent/sessions/<proj>/*.jsonl` | 48 个文件 |
| 裁剪观测日志 | `~/.superpi/context-guard.log.jsonl` | 240 轮（滚动上限） |

### 1.2 决定性数字

| 指标 | 实测值 |
| --- | --- |
| `before` 范围 | **2,849,944 ~ 2,919,604**（几乎不涨） |
| `after` 范围 | 459,765 ~ 699,804（被压进预算） |
| 压缩比 | **4.40x**（恒定） |
| `imagesDropped` 的取值集合 | **只有一个：117** |
| 会话中实际图片总张数 | **118 张，全部在 `toolResult`** |
| `trimmed=true` 占比 | **240/240 = 100%** |

### 1.3 五类构成（口径与 `breakdownMessages` 一致）

| 类别 | tokens | 占比 |
| --- | --- | --- |
| **图片**（118 张 toolResult 截图） | 1,416,000 | **47.0%** |
| 工具调用参数 | 573,626 | 19.0% |
| 工具结果文本 | 517,177 | 17.2% |
| thinking | 439,022 | 14.6% |
| 正文 | 66,596 | 2.2% |
| **user（人类真正说的话）** | **939** | **0.03%** |

人类输入占 0.03%。**会话 99.97% 的上下文是 agent 自己产生的中间产物。**

---

## 2. 为什么 `context` 层永远治不好

pi 对 `context` 事件的契约原文（`docs/extensions.md:815`）：

> Fired before each LLM call. **Modify messages non-destructively.**

`non-destructively` 是 pi 的刻意设计（保护原始记录），本身正确。
但它的必然后果是：**任何只在 `context` 层做的清理，都是每轮重算的临时视图。**

```
截图 → read 工具 → 12000 tokens 位图写入 toolResult（永久）
  → context 每轮从 285 万原始历史重算
  → 丢掉 117 张（= 118 − 保留 1）
  → 压到 65 万发送
  → 历史本体仍是 285 万
  → 下一轮重复
```

`before` 恒定、`imagesDropped` 恒定 —— 这两个不变量就是上述循环的数学指纹。

---

## 3. 为什么 `tool_result` 是唯一正确的位置

pi 对 `tool_result` 的契约原文（`docs/extensions.md:1040`）：

> Fired after tool execution finishes and **before** `tool_execution_end` plus the final
> tool result message events are emitted. **Can modify result.**
>
> Handlers can return partial patches (`content`, `details`, `structuredContent`,
> `isError`, or `usage`); omitted fields keep their current values.

这是唯一在「图片进入历史**之前**」触发的钩子。在这里处置，位图根本不会进入历史。

---

## 4. 实现与坑

### 4.1 必须按「会话累计」而不是「单条消息」

**第一版做错了**：按「单条 `toolResult` 内的图片数」限额。

实测收益 **0** —— 真实形状是 **118 条消息各含 1 张图**，不是 1 条含 118 张。
每条都没超限额，于是一条都不改。

这个错误由探针 `_scratch/probe-write-limit-gain.mjs` 当场抓出，**不是靠推理发现的**。
所以「先写探针量收益」这一步不能省。

### 4.2 累计状态必须由扩展自己记账

`tool_result` 的 event **不含会话历史**（只有当前这一条结果），
pi 也**没有**提供改写历史的 API。所以「本会话已留下几张图」只能进程内累计。

**必须在会话切换时清零**：`/new`、`switch_session`、`fork`、`clone` 在同一进程里
换掉整棵会话树。不清零会把旧会话的记账带进新会话，让新会话一开始就
"额度已满、一张图都不留" —— 比不限额更糟的静默失效。

### 4.3 复用 `keepRecentImagesPerTurn`，不新增配置

「保留几张图」是一个决策，不能有两个真源。
若写入时按一个数、读时按另一个数，两套规则会互相打脸（写时留 4、读时又丢 3）。

---

## 5. 收益（探针实测）

真实会话形状：118 条 `toolResult`，各含 1 张图（12000 tokens/张）。

| 限额 | 历史中图片 tokens | 掉落张数 | 相对现状 |
| --- | --- | --- | --- |
| 0 | 0 | 118 | -100.0% |
| 1 | 12,000 | 117 | -99.2% |
| 2 | 24,000 | 116 | -98.3% |
| **4（选定）** | **48,000** | **114** | **-96.6%** |
| 8 | 96,000 | 110 | -93.2% |
| 16 | 192,000 | 102 | -86.4% |

**选 4 的理由**：1 与 4 的收益差别只有 2.6 个百分点（因为 118 张里绝大多数是
历史累积，不是当前轮），但 4 保住了「同时对比几张图」的能力。这是净收益判断，
不是折中。

---

## 6. 与 DSML 的关系（明确标注边界）

**不能**说"上下文超载导致 DSML"。理由：
`trimmed=true` 在 240/240 轮里都成立 —— 一个覆盖全部样本的条件，
无法解释只在少数样本出现的结果。若裁剪是原因，DSML 应出现在每一轮。
这是相关，不是因果（0.15.4 已经在这上面误判过一次）。

**可以**说"模型每轮都在一份被削掉 49% 的陌生上下文上工作"，
这为退化提供了背景条件，但不构成充分证明。

---

## 7. 未做的验证（诚实标注）

1. **没有做对照实验**：同一段对话、开关写入时限额各跑 N 轮，统计 DSML 率。
   目前只有"理论上上下文更干净"的推论，没有"DSML 因此减少"的实测。
2. **改动后无历史可比**：现有 118 张图的历史不会变，只有新会话受益。
3. **多图对比能力的实际影响未测**：只留 4 张是否真的够用，需要在真实任务里观察。

以上三条是这一版改动的已知不确定处。
